# PRD: AI Service Desk MVP

## 1. Назначение и статус

Требования исходного MVP и расширение на панель Agent/Admin одобрены пользователем. Документ описывает согласованный scope, но сам по себе не подтверждает production-готовность; детали реализации и эксплуатационные ограничения отмечены ниже.

## 2. Цели и границы MVP

### Цели

- Принимать текстовые обращения пользователей через Telegram и API.
- Использовать Gemini для классификации обращения и поиска ответа по базе знаний.
- Отвечать самостоятельно только при достаточной уверенности и подтверждении материалами базы знаний.
- Создавать тикет для специалиста, если требуется человек, ответ не подтверждён или автоматическая обработка не удалась.
- Давать Support Agent и Admin API и внутреннюю панель для работы с тикетами; Admin может загружать документы базы знаний.
- Обеспечить локальный запуск API и PostgreSQL/pgvector через Docker Compose и применение схемы через Alembic.
- Добавить компактную внутреннюю панель Agent/Admin, server-rendered в FastAPI с Jinja2/HTMX и доступную только из доверенной сети.

### Входит в MVP

- FastAPI, PostgreSQL с pgvector, Alembic, Gemini, Telegram Bot API и опциональный n8n workflow.
- Статические Bearer-токены трёх ролей: User, Support Agent и Admin.
- Создание, просмотр и изменение тикетов; добавление комментариев.
- Внутренняя очередь с поиском по всей базе, фильтрами и пагинацией по 25 тикетов; детали, история сообщений, ответы и изменение статуса, приоритета и решения.
- Вкладка управления документами базы знаний только для Admin: список метаданных и загрузка поддерживаемых файлов через имеющиеся API.
- Server-rendered UI FastAPI (Jinja2/HTMX), доступ только из доверенной сети. Без клиентского API-токена.
- Загрузка PDF, TXT и Markdown до 10 MB; извлечение текста и индексация embeddings.
- RAG-ответ с источником либо детерминированная эскалация в тикет.
- Health endpoints и сводка количества тикетов по статусам.
- Персональный вход специалиста, взятие тикета в работу и фильтр My tickets.

### Не входит в MVP

- User-facing UI; в панель входят только Support Agent и Admin.
- Production SSO/OIDC, администрирование сотрудников и надёжная привязка Telegram identity к корпоративной учётной записи.
- OCR сканов, хранение оригиналов документов и поддержка форматов кроме PDF/TXT/Markdown.
- Автоматическая разблокировка аккаунтов, изменение VPN/учётных записей или другие привилегированные действия AI.
- Переназначение тикета другим сотрудником, история назначений, SLA и эскалация по времени.
- Гарантированная доставка через очередь/outbox, отказоустойчивый multi-instance deployment и целевые показатели доступности/нагрузки.
- Аналитика, выходящая за текущую сводку тикетов по статусам.
- Управление документами сверх просмотра метаданных и загрузки: удаление, изменение, переиндексация и OCR.
- Сложные отчёты, массовые операции и пользовательские настройки панели.
- Выдача API-токена браузерному JavaScript, хранение токена в localStorage/sessionStorage, а также доступ к панели из недоверенной сети.

**Граница UI/API.** Маршруты `/ui/...` обслуживают HTML-страницы и формы. Панель переиспользует серверную логику и выполняет поиск и фильтрацию в БД. Публичный REST-список возвращает до 100 последних результатов с фильтром `status`.

**Сессия панели:** сотрудник вводит общий токен роли или персональный токен из `PANEL_AGENT_TOKENS`. Сервер выдаёт подписанную cookie с ролью, CSRF-токеном, сроком действия 8 часов и именем при персональном входе. Cookie — `HttpOnly`, `Secure`, `SameSite=Lax`; Bearer-токен не сохраняется в cookie или browser storage и не возвращается клиенту. Ключ подписи `SESSION_SIGNING_SECRET` обязателен, без dev fallback. Все изменяющие UI-запросы, включая login/logout, требуют CSRF-проверки. Logout очищает cookie; смена ключа отзывает все сессии, а отдельная stateless-сессия не может быть отозвана досрочно. Доверенная сеть и HTTPS должны обеспечиваться ingress/firewall. Общие role-токены не дают персональной идентичности.

## 3. Роли и права доступа

Роли определяются статическими Bearer-токенами из конфигурации. Это MVP-механизм, не корпоративная идентификация.

| Возможность | User | Support Agent | Admin |
|---|---:|---:|---:|
| Создать тикет | Да | Да | Да |
| Список тикетов | Только свои | Все, до 100 записей | Все, до 100 записей |
| Просмотреть тикет | Только свой | Любой | Любой |
| Добавить комментарий | Только к своему тикету | К любому тикету | К любому тикету |
| Изменить статус, приоритет, решение | Нет | Да | Да |
| Анализировать обращение через AI endpoint | Нет | Да | Да |
| Просматривать список документов через API | Нет | Да | Да |
| Просматривать вкладку документов в UI | Нет | Нет | Да |
| Загружать документы через API/UI | Нет | Нет | Да |
| Просматривать сводку по статусам | Нет | Да | Да |

**Контекст API.** Формы панели и REST-операции используют общие правила записи сообщений и обновления тикетов. Допустимые приоритеты и статусы перечислены в [контракте](openapi.yaml).

**Идентификация.** User API проверяет соответствие заголовка X-Telegram-User-ID персональному токену из USER_API_TOKENS. Общие токены Agent/Admin сохраняют ограничение атрибуции сотрудника.

## 4. Пользовательские сценарии

### 4.1 Telegram-пользователь

1. Пользователь отправляет текст боту.
2. FastAPI проверяет секрет webhook, валидирует update и сохраняет входящее сообщение с внешним ID.
3. Если настроен n8n, он запускает внутреннюю обработку. FastAPI обрабатывает сообщение напрямую при ошибке вызова n8n или если n8n не настроен.
4. Система классифицирует обращение, ищет релевантные фрагменты базы знаний и пытается сформировать ответ только по ним.
5. Если все условия автономного ответа выполнены, пользователь получает ответ с названием источника.
6. Иначе создаётся тикет, и пользователь получает его номер.
7. Пользователь может просматривать собственные тикеты и историю сообщений, а также добавлять сообщения через API с проверкой владельца.

### 4.2 Специалист поддержки

1. Support Agent открывает внутреннюю панель из доверенной сети и проходит согласованный механизм сессии.
2. Панель ищет по всей очереди по номеру, теме и описанию. Фильтр статуса применяется до пагинации. На странице отображается до 25 тикетов.
3. Специалист открывает тикет, видит детали и хронологию сообщений, добавляет ответ и изменяет статус, приоритет или resolution.
4. Admin выполняет те же действия и дополнительно открывает доступную только ему вкладку документов: просматривает метаданные и загружает PDF/TXT/Markdown размером до 10 MB.
5. Назначение конкретного специалиста, поиск по всей очереди, пагинация и управление документами сверх перечисленного не входят в scope.

### 4.3 Внутренняя панель: ограничения и безопасная сессия

Панель — HTML, формируемый FastAPI/Jinja2; локально поставляемый HTMX улучшает навигацию и формы, сохраняя их работоспособность без JavaScript. Она не предоставляет User роль и не открывается вне доверенной сети. UI-маршруты FastAPI используют серверную проверку роли и существующую бизнес-логику; браузер не вызывает API с общим Bearer-токеном. Login принимает общий токен роли или персональный токен специалиста в теле HTTPS-запроса. Cookie содержит роль, CSRF-токен, срок действия 8 часов и имя при персональном входе. Cookie — `HttpOnly`, `Secure`, `SameSite=Lax`; сам Bearer-токен не сохраняется в cookie, HTML, JavaScript, URL или Web Storage. `SESSION_SIGNING_SECRET` обязателен, без fallback. Все изменяющие UI-запросы, включая login/logout, требуют CSRF-проверки. Logout очищает cookie; stateless-сессию нельзя отозвать отдельно до истечения срока, но смена ключа отзывает все сессии. HTTPS и allowlist доверенной сети применяются на ingress/firewall. Событие взятия тикета в работу содержит имя специалиста. Атрибуция остальных действий остаётся ограниченной.

## 5. Сценарии обращений и маршрутизация

| Сценарий | Предлагаемая категория/подкатегория | Отдел по текущему коду | Пробел/оговорка |
|---|---|---|---|
| VPN | network / vpn | Network Support | Самостоятельная диагностика только при наличии подтверждённой статьи |
| Интернет | network / internet | Network Support | Самостоятельная диагностика только при наличии подтверждённой статьи |
| Авторизация | account / authentication | System Administration | Маршрут зависит от меток классификатора |
| Заблокированный аккаунт | account / authentication | System Administration | Отдельного правила для blocked account нет; подтвердить, что он относится к этой категории |
| Принтер | hardware / printer | Hardware Support | Самостоятельная диагностика только при наличии подтверждённой статьи |
| Корпоративное ПО | software / software | Software Support | Конкретные названия систем и маршруты в ТЗ не заданы |
| Безопасность, критический приоритет | security | Security Team | В коде проверяется слово `security` в категории/подкатегории |
| Неизвестная категория | other/неизвестная | Software Support | Текущий маршрут по умолчанию; требует явного согласования |

Маршрутизация основана на точных категориях/подкатегориях из `app/main.py`, а не на свободном распознавании названий. Департамент выбирается по категории, затем по подкатегории, иначе используется `software_support`. Набор меток классификатора и default-маршрут необходимо подтвердить до реализации.

## 6. Проверяемые правила ответа и эскалации

Обозначения:

- `confidence_threshold` по умолчанию равен `0.65` и настраивается конфигурацией.
- Подходящими считаются найденные фрагменты с `score >= 0.35`.
- «Подтверждённый ответ» — ответ модели не равен `NO_CONFIRMED_SOLUTION` и сформирован с инструкцией использовать только переданные выдержки. Это не является формальной гарантией корректности модели.

Система создаёт тикет, если выполняется **хотя бы одно** условие:

1. Классификация устанавливает `needs_human = true`.
2. Приоритет равен `critical`.
3. `confidence < confidence_threshold`.
4. Нет найденных фрагментов с `score >= 0.35`.
5. Генератор ответа возвращает ровно `NO_CONFIRMED_SOLUTION`.
6. Классификация, embedding, поиск или генерация завершаются ошибкой.

Самостоятельный ответ разрешён только если **все** условия соблюдены: `needs_human = false`, приоритет не `critical`, уверенность не ниже порога, найден хотя бы один подходящий фрагмент, получен подтверждённый ответ. Ответ содержит название использованных источников.

При технической ошибке система должна явно сообщить об эскалации и не выдавать неподтверждённый ответ. Создание тикета также может завершиться ошибкой, например при недоступности БД; в таком случае нельзя сообщать пользователю, что тикет создан.

## 7. Функции и acceptance criteria

### 7.1 Аутентификация и авторизация

- **Given** запрос без токена или с неверным токеном, **When** он обращается к защищённому endpoint, **Then** API возвращает `401`.
- **Given** User обращается к endpoint, доступному только Agent/Admin, **When** роль проверяется, **Then** API возвращает `403`.
- **Given** User API работает с тикетами, **When** запрашивается или изменяется чужой тикет, **Then** содержимое тикета не раскрывается и операция отклоняется.
- Для User API несовпадение X-Telegram-User-ID с идентификатором, привязанным к Bearer-токену, возвращает HTTP 401.

### 7.2 Тикеты и сообщения

- **Given** корректный запрос создания тикета от разрешённой роли, **When** API его принимает, **Then** создаётся тикет с уникальным номером `SD-...` и начальным сообщением.
- **Given** User запрашивает список или конкретный тикет, **When** данные возвращаются, **Then** доступны только тикеты этого User.
- **Given** Agent/Admin запрашивает очередь, **When** API формирует список, **Then** результат содержит не более 100 тикетов и может фильтроваться по статусу.
- **Given** Support Agent/Admin открывает очередь панели, **When** данные загружаются, **Then** UI показывает до 25 записей на странице и счётчик результатов по текущим фильтрам.
- **Given** список очереди получен, **When** специалист задаёт поиск, **Then** поиск выполняется без учёта регистра по номеру тикета, теме и описанию во всей очереди до пагинации.
- **Given** специалист выбирает статусный фильтр, **When** очередь обновляется, **Then** используются только статусы, поддерживаемые текущим API: `open`, `in_progress`, `waiting_for_user`, `resolved`, `closed`.
- **Given** Agent/Admin открывает тикет из очереди, **When** детали загружены, **Then** UI показывает данные тикета и хронологию сообщений.
- **Given** Agent/Admin отправляет ответ в тикет, **When** сообщение успешно принято обработчиком формы, **Then** оно появляется в хронологии с автором/временем, если эти метаданные возвращает API; при ошибке UI сообщает об ошибке и не показывает ответ как сохранённый.
- **Given** Agent/Admin изменяет тикет, **When** он сохраняет форму, **Then** UI предлагает только статусы `open`, `in_progress`, `waiting_for_user`, `resolved`, `closed`, приоритеты `low`, `medium`, `high`, `critical` и resolution длиной не более 20 000 символов; status/priority не могут быть `null`. Сохранение использует ту же валидацию, что и REST PATCH.
- **Given** Agent/Admin передаёт допустимый статус, приоритет или решение, **When** PATCH проходит валидацию, **Then** изменения сохраняются и создаётся audit log.
- **Given** PATCH содержит неизвестное поле, пустое обновление или `null` для поля, которое не может быть null, **When** запрос валидируется, **Then** API отклоняет запрос без изменения тикета. Это требование фиксирует выявленный дефект схемы/обработчика.
- **Given** сообщение добавляется к тикету, **When** роль — User, **Then** запись разрешается только владельцу; для Agent/Admin — по существующим правам.
- **Given** User читает историю сообщений, **When** существующий endpoint получения сообщений авторизует запрос, **Then** User видит историю только собственного тикета, а Agent/Admin — историю доступных им тикетов.

### 7.3 База знаний и RAG

- **Given** Admin загружает непустой PDF/TXT/Markdown размером не более 10 MB с извлекаемым текстом, **When** Gemini embeddings успешно созданы, **Then** документ индексируется, и фрагменты доступны поиску.
- **Given** загрузчик получает неподдерживаемый тип, файл больше 10 MB или документ без извлекаемого текста, **When** проверка выполняется, **Then** API возвращает соответственно `415`, `413` или `400`, не публикуя документ как индексированный.
- **Given** Agent/Admin запрашивает список документов, **When** роль разрешена, **Then** API возвращает метаданные документов без содержимого фрагментов.
- **Given** обращение ищется в базе знаний, **When** строится результат, **Then** поиск исключает документы не в статусе `indexed` и embeddings другой модели.

### 7.4 AI-анализ и эскалация

- **Given** все условия автономного ответа из раздела 6 соблюдены, **When** сообщение обработано, **Then** пользователь получает ответ, основанный на подходящих фрагментах, с названием источника, а тикет не создаётся.
- **Given** любое условие эскалации из раздела 6 соблюдено, **When** сообщение обработано, **Then** создаётся тикет с классификацией и исходным текстом, а пользователю сообщается номер тикета.
- **Given** Gemini или RAG недоступны, **When** обработка завершается ошибкой, **Then** система пытается создать тикет и не сообщает об успешной автоматической диагностике.
- **Given** запрос анализа выполняет User, **When** проверяется роль, **Then** endpoint недоступен; Agent/Admin могут вызвать анализ.

### 7.5 Telegram и n8n

- **Given** webhook вызван с отсутствующим или неверным Telegram secret, **When** запрос проверяется, **Then** API возвращает `401` и не сохраняет сообщение.
- **Given** Telegram повторно доставляет update с тем же внешним ID, **When** update обрабатывается, **Then** второе входящее сообщение и второй тикет не создаются.
- **Given** `N8N_WEBHOOK_URL` задан, **When** поступает новое Telegram-сообщение, **Then** workflow вызывается с настроенным ingress token; при отсутствии URL используется прямой путь обработки.
- **Given** n8n недоступен, **When** он настроен как обработчик, **Then** API явно сообщает о сбое постановки в обработку и не возвращает успешный результат постановки.
- **Given** обработка уже завершена, **When** сообщение приходит повторно, **Then** ранее сохранённый ответ может быть отправлен повторно без повторного анализа и создания тикета.

### 7.6 Эксплуатационные endpoints

- **Given** процесс API запущен, **When** вызывается `/health/live`, **Then** endpoint возвращает состояние процесса.
- **Given** PostgreSQL доступен, **When** вызывается `/health/ready`, **Then** API выполняет проверочный запрос и сообщает готовность; при недоступности БД endpoint отвечает HTTP 503.
- **Given** Agent/Admin запрашивает overview, **When** запрос авторизован, **Then** возвращается количество тикетов по статусам; User не имеет доступа.

### 7.7 Внутренняя панель Support Agent/Admin

- **Given** сотрудник открывает панель из недоверенной сети, **When** сетевые ограничения применяются, **Then** доступ к панели и её защищённым действиям блокируется.
- **Given** Agent/Admin прошёл утверждённую аутентификацию панели, **When** сервер формирует страницу, **Then** ответ — server-rendered HTML/Jinja2 с HTMX; роль User не имеет входа или UI-раздела.
- **Given** API Bearer-токен используется панелью, **When** страница или HTMX-ответ возвращается браузеру, **Then** токен отсутствует в HTML, JavaScript, URL и Web Storage; браузер взаимодействует с FastAPI, а не с API от имени общего токена.
- **Given** изменяющий запрос отправлен из браузера, **When** сервер проверяет synchronizer CSRF-token, **Then** запрос без действительного подтверждения отклоняется до изменения данных; это правило распространяется на login/logout и все ticket/knowledge формы.
- **Given** пользователь с ролью Agent открывает раздел базы знаний, **When** проверяется доступ UI и сервером, **Then** вкладка/операции документов недоступны; Admin видит список метаданных и загрузку.
- **Given** Admin загружает поддерживаемый PDF/TXT/Markdown размером до 10 MB, **When** существующий API принимает загрузку, **Then** UI показывает фактический результат/статус API; при отказе файл не обозначается как успешно индексированный.
- **Given** Admin пытается загрузить неподдерживаемый тип или файл больше 10 MB, **When** форма проверяет запрос, **Then** загрузка отклоняется с понятным сообщением, соответствующим ответу API.
- **Given** запрошена функция вне доступных API (например, удаление документа), **When** пользователь работает в панели, **Then** функция не отображается как доступная и операция не имитируется на клиенте.
- **Given** API или БД недоступны, **When** панель читает либо изменяет данные, **Then** она показывает безопасное сообщение об ошибке и не подтверждает неуспешную операцию как завершённую.

## 8. Нефункциональные требования

### Безопасность

- Секреты и токены задаются окружением, не включаются в репозиторий и не возвращаются клиенту в ошибках.
- Сравнение webhook/workflow/Bearer секретов выполняется безопасным сравнением; Telegram webhook требует секретного заголовка.
- Проверка владения применяется ко всем операциям User над тикетами и перепиской.
- Персональные токены User API выдаются администратором через USER_API_TOKENS. Доступ разворачивается через HTTPS в доверенной сети.
- Ответ AI не утверждает, что выполнено административное действие; контент запроса и документы считаются недоверенными инструкциями.
- Доступ к Gemini с данными обращений разрешён владельцем проекта для тестового MVP. Передача чувствительных данных и условия тарифа должны оставаться явно задокументированными.
- Панель доступна только из доверенной сети; сетевое ограничение не заменяет авторизацию.
- API-токен хранится только на серверной стороне; он не раскрывается в HTML/JavaScript/URL/Web Storage и не передаётся браузеру.
- Согласованная session cookie: подписанная, `HttpOnly`, `Secure`, `SameSite=Lax`, срок 8 часов; обязательны `SESSION_SIGNING_SECRET` без fallback и CSRF-защита всех изменяющих UI-запросов, включая login/logout.
- Agent/Admin UI разделы и операции проверяются сервером при каждом запросе, а не только скрываются в интерфейсе. Admin-only управление документами защищается на сервере.
- Сессии не создают персональную идентичность: поскольку текущие Bearer-токены общие для роли, ограничения атрибуции автора и аудита должны быть видны оператору.

### Наблюдаемость

- `/health/live` и `/health/ready` различают доступность процесса и готовность БД.
- Ошибки внешних интеграций должны быть видны в серверных логах без записи секретов.
- Изменения тикетов фиксируются в audit log; actor и требуемый срок хранения записей аудита не определены текущим API и требуют решения.
- Метрики, трассировка и целевые показатели времени ответа/доступности в исходных требованиях не заданы.
- Ошибки панели и API логируются с correlation/request ID, ролью и видом операции, но без секретов, CSRF/session значений, токенов и полного текста сообщений/документов. Персональная атрибуция при общих role-токенах недоступна.
- Для отказа в доступе, ошибок чтения/сохранения и ошибок загрузки UI должен показывать безопасный результат; детали исключений остаются только в защищённых серверных логах.

### Отказоустойчивость

- Ошибка AI не приводит к неподтверждённому ответу; система пытается эскалировать запрос тикетом.
- Уникальность внешнего Telegram message ID предотвращает повторную вставку одного update.
- При обработке сообщения приложение использует блокировку строки в БД, сериализующую конкурирующую обработку этой записи. Это не обеспечивает durable outbox, гарантированную доставку или координацию всех внешних эффектов; n8n-вызов остаётся синхронным.
- При недоступной БД операция не должна изображаться как успешно завершённая.
- При недоступности API/БД панель должна сохранять работоспособность чтения оболочки/сообщения об ошибке, не показывать устаревшие данные как подтверждённое актуальное состояние и не повторять изменяющий запрос автоматически без подтверждённой идемпотентности.
- Время ответа, пропускная способность, RPO/RTO и целевая доступность не согласованы; численные гарантии не задаются этим PRD.

## 9. Хранение данных

Решение для MVP: хранить закрытые тикеты и связанные сообщения 365 дней после закрытия; открытые тикеты не удалять автоматически; документы базы знаний и audit logs хранить 365 дней с даты создания. Автоматическое удаление по этой политике необходимо реализовать. Правило для тикетов, которые повторно открыты в течение срока хранения, — отсчитывать 365 дней заново после следующего закрытия.

## 10. Известные ограничения и эксплуатационные шаги

- Панель входит в одобренный scope; первоначальная реализация и проверка выполняются в рамках текущей задачи.
- Compose публикует API только на loopback. Перед сетевым развертыванием оператор должен настроить HTTPS и allowlist доверенной сети на ingress/firewall.
- Общие Agent/Admin role-токены не дают персональной идентичности; stateless-сессию нельзя отозвать отдельно до истечения 8-часового срока. Ротация `SESSION_SIGNING_SECRET` отзывает все панельные сессии.
- Глобальный поиск и пагинация доступны в панели. REST-список ограничен 100 тикетами.
- API не задаёт workflow-переходы статусов; UI принимает перечисленные значения, но не добавляет отдельные правила перехода.
- Управление базой знаний ограничено списком метаданных и загрузкой; удаление/переиндексация не входят в scope.

## 11. Уведомление в Telegram об ответе сотрудника

**Статус.** Реализовано в панели с миграцией `0004_telegram_reply_notification`. Функция относится только к ответам Support Agent/Admin в панели и Telegram private (1:1) chats. Она не добавляет публичные endpoints.

### Цель и границы MVP

После сохранения ответа Support Agent или Admin в тикете система отправляет полный текст ответа пользователю в тот же Telegram private chat, из которого поступило исходное обращение, если тикет подходит под условия отправки.

В scope:

- Отправка только ответов, добавленных Support Agent/Admin через форму ответа панели.
- Для новых входящих Telegram-обращений сохраняется доверенный `message.chat.id` из webhook и связь этого идентификатора с тикетом. Для этой функции поддерживаются только updates с `message.chat.type=private` (диалог 1:1).
- Получатель берётся только из сохранённого `message.chat.id`. Использовать `telegram_user_id` как fallback запрещено.
- Сначала сообщение ответа сохраняется в тикете, затем выполняется ровно один вызов Telegram `sendMessage` с полным ответом без усечения и как plain text.
- Для eligible Telegram tickets длина ответа свыше 4 000 символов отклоняется до сохранения сообщения.
- Связь с Telegram chat id хранится и удаляется вместе с тикетом согласно существующей retention policy (365 дней после закрытия тикета; открытые тикеты автоматически не удаляются).
- UI отдельно показывает факт сохранения ответа и результат отправки. Отсутствие подтверждения доставки не отменяет сохранённый ответ.

Не входят в MVP: группы и иные типы Telegram-чатов; уведомления через API или другие каналы; уведомления при изменении статуса/приоритета/resolution или на сообщения пользователя; новое согласие/opt-in workflow; change notifications; подтверждение прочтения или гарантия получения; автоматические retries, durable outbox и гарантированная доставка; новые public endpoints и дополнительные полномочия ролей.

### Роли и user journeys

| Роль | Действия в рамках функции |
|---|---|
| User (Telegram-пользователь) | Получает полный текст ответа в private-чате, связанном с подходящим Telegram-тикетом. Новых действий или интерфейса User нет. |
| Support Agent | Через существующую панель сохраняет ответ; для подходящего тикета система после сохранения выполняет одну попытку `sendMessage`. |
| Admin | Выполняет тот же сценарий, что Support Agent; дополнительных полномочий по получателю или доставке нет. |

**Telegram-пользователь**

1. Пользователь отправляет боту текстовое обращение в private 1:1 chat; webhook передаёт `message.chat.id`, и система сохраняет этот chat id со связанным тикетом при его создании.
2. При эскалации пользователь ожидает ответ в том же private-чате; сроки ответа и SLA не обещаются.
3. После ответа сотрудника система отправляет полный plain-text ответ, если тикет eligible и длина не превышает 4 000 символов. При неподтверждённой отправке гарантии получения нет.

**Support Agent / Admin**

1. Сотрудник проходит существующую авторизацию панели и открывает тикет.
2. Для eligible Telegram ticket ответ длиной не более 4 000 символов сначала сохраняется в историю, затем система один раз вызывает `sendMessage`.
3. UI показывает сохранение отдельно от результата отправки: подтверждённый ответ Telegram API, либо сохранённый ответ с неподтверждённой доставкой, либо отсутствие отправки для неeligible тикета/отсутствующей конфигурации.

### Детерминированные правила и обработка ошибок

Тикет eligible для Telegram-отправки тогда и только тогда, когда он связан с входящим Telegram обращением из private 1:1 chat и для него сохранён `message.chat.id`, полученный из доверенного webhook. Группы и другие chat types не eligible. Наличие только `telegram_user_id` не делает тикет eligible. Старые тикеты без сохранённого `message.chat.id` не получают уведомление; fallback на `telegram_user_id` запрещён.

Отправка выполняется только для ответа, добавляемого Agent/Admin через действие ответа панели, если тикет eligible и настроен `TELEGRAM_TOKEN`. Она не зависит от статуса тикета. Для eligible тикета ответ длиной более 4 000 символов отклоняется до сохранения; система не отправляет усечённый текст и не разбивает ответ на несколько сообщений. Для допустимого ответа сначала завершается сохранение сообщения тикета, после чего выполняется ровно один вызов `sendMessage` на сохранённый `message.chat.id` с полным содержимым ответа как plain text.

Если ответ не удалось сохранить, `sendMessage` не вызывается. Если Telegram отклонил запрос, произошёл timeout, ответ Telegram некорректен либо не подтверждает `ok=true`, доставка считается **не подтверждённой**: сообщение остаётся сохранённым, а UI отдельно сообщает о сохранении и неподтверждённой доставке. Автоматических повторов нет; повторно отправлять сохранённый ответ автоматически нельзя. При отсутствии `TELEGRAM_TOKEN` сообщение остаётся сохранённым, отправка не вызывается, UI показывает, что уведомление не отправлено из-за конфигурации. Успешный ответ Telegram API означает только принятие API-запроса, но не прочтение и не гарантию получения пользователем.

### Acceptance criteria

- **Given** Telegram webhook получает update с `message.chat.type=private` и создаёт тикет, **When** сохраняется связь обращения с тикетом, **Then** в тикете сохранён ровно исходный `message.chat.id` из update; `telegram_user_id` не используется вместо него.
- **Given** webhook получает update с chat type, отличным от `private`, **When** система определяет eligible для этой функции, **Then** такой чат не становится eligible получателем уведомления Agent/Admin.
- **Given** тикет eligible, `TELEGRAM_TOKEN` настроен и ответ не превышает 4 000 символов, **When** Agent отправляет ответ через панель и сохранение успешно, **Then** сообщение появляется в истории до единственного вызова `sendMessage`, вызов адресован сохранённому `message.chat.id`, а его plain-text payload в точности равен полному сохранённому тексту ответа.
- **Given** те же условия, **When** Admin отправляет ответ через панель, **Then** выполняется тот же единственный вызов и применяются те же правила адресата и текста, что и для Agent.
- **Given** ответ eligible Telegram ticket содержит 4 001 или более символов, **When** Agent/Admin отправляет ответ, **Then** запрос отклоняется до сохранения, история тикета не получает это сообщение, а Telegram `sendMessage` не вызывается.
- **Given** тикет не eligible, включая старый Telegram-тикет без сохранённого `message.chat.id`, либо тикет не создан из Telegram, **When** Agent/Admin сохраняет ответ, **Then** `sendMessage` не вызывается и `telegram_user_id` не используется как fallback; ответ обрабатывается согласно обычным правилам сохранения панели.
- **Given** User добавляет сообщение через API или Agent/Admin меняет только статус, приоритет либо resolution, **When** операция завершается, **Then** отправка уведомления об ответе сотрудника не производится.
- **Given** сохранение ответа завершается ошибкой, **When** панель обрабатывает отправку, **Then** запись ответа отсутствует в истории и `sendMessage` не вызывается.
- **Given** ответ успешно сохранён для eligible тикета, но `sendMessage` отклонён, истёк timeout, получен некорректный ответ или `ok` не равен `true`, **When** панель показывает результат операции, **Then** ответ остаётся в истории, UI отдельно обозначает «сохранён» и «доставка не подтверждена», и автоматический повторный вызов не выполняется.
- **Given** `TELEGRAM_TOKEN` не настроен, **When** Agent/Admin сохраняет допустимый по длине ответ в eligible Telegram ticket, **Then** ответ остаётся в истории, вызов Telegram не выполняется, а UI показывает, что уведомление не отправлено из-за конфигурации.
- **Given** Telegram API возвращает валидный ответ с `ok=true`, **When** вызов завершается, **Then** UI может показать подтверждение принятия запроса Telegram API, но не заявляет о прочтении или гарантированном получении сообщения.
- **Given** ответ отправляется в Telegram, **When** формируется запрос и операция логируется, **Then** используется plain text без усечения/разбиения/parse mode, а логи не содержат bot token или полного текста ответа.
- **Given** тикет удаляется по существующей retention policy, **When** выполняется удаление после срока хранения 365 дней, **Then** связанный с тикетом `message.chat.id` удаляется вместе с тикетом; открытый тикет автоматически не удаляется.

### Безопасность, наблюдаемость и отказоустойчивость

- Использовать существующие серверные проверки роли панели, cookie/CSRF и доверенной сети; не передавать Bot API token браузеру.
- Получатель определяется только сохранённым `message.chat.id` из webhook для private 1:1 chat. Не принимать получателя из формы, ответа, клиентских заголовков или `telegram_user_id` fallback.
- Сохранять связь chat id только вместе с тикетом и удалять её по существующей retention policy 365 дней после закрытия тикета; открытые тикеты сохраняются.
- Логировать результат отправки, тикет/корреляционный идентификатор и класс ошибки без токенов, полного текста ответа и чувствительных деталей ответа Telegram.
- Сбой Telegram не отменяет сохранение ответа. UI не должен объединять статус сохранения со статусом доставки или утверждать доставку при timeout/ошибке.
- Выполнять не более одного вызова `sendMessage` на одну отправку ответа из панели; автоматических retries и outbox нет. Получение `ok=true` подтверждает ответ Telegram API, а не чтение или гарантированное получение пользователем.
